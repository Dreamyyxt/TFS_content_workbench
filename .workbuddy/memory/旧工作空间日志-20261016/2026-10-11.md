### 事故修复：「选取片段超出视频长度」（三层都漏）

现象：用户传 3 段视频、目标 20 秒，模型排了 5.5 / 7.5 / **7.0** 秒，
但第 3 段素材实际只有 **6.68 秒** → 本机执行器 `jianying_edit.py:215` 报错判失败。

**根因不是模型算错 0.32 秒，而是校验闸门三层同时失效：**

1. `jianying-studio.js` 把 `assets`（上传响应，只有 id/name/ext/type/size，**没有 duration**）
   传给 `EditPlan.validate()`；带 ffprobe 时长的 `inspected` 只喂了模型，没给校验用。
2. `edit-plan.js` 的 `validate()` **压根没有「片段不得超出素材长度」这条检查**
   （因为拿到的素材表里没有 duration，写了也没用）。
3. `jianying-api.js` 的 `jobs POST` 二次校验同样用 `state.assets`（也没有 duration）。

**修复（4 处，全部已过测试）：**

- `edit-plan.js`：在**总时长补差之后**加最后一道检查 ——
  `source_start_us + duration_us <= round(a.duration*1e6) + 1000`（容差与执行器一致）；
  `duration` 非有限数（图片）直接跳过，所以老调用方不受影响。
  报错格式：`第 N 个镜头「文件名」从 X 秒起要 Y 秒，但该素材只有 Z 秒…`
- `app.js`：`WorkbenchEditPlanner(input, onProgress, feedback)` 新增第三参；
  feedback 存在时往 messages 里 push `{role:'assistant', 上一版 JSON}` +
  `{role:'user', 失败原因 + 要求按素材真实 duration 重排}`。提示词里把时长约束
  改成加粗硬约束（"6.68 秒就写 6.5 秒，不要写 7 秒"）。
- `jianying-studio.js`：改用 `merged`（inspected + description）做校验输入；
  planner+validate 包进**最多 3 轮自愈重排**循环，失败原因回喂，3 轮仍不合格才抛。
- `jianying-api.js`：`assets/inspect` 里 `Object.assign(a, info)` 把探测到的

### 口播超时长：补上第二道闸门（用户截图报「口播超过目标时长」）

第二次真实失败：计划过了视觉与镜头校验，但模型写了 156 字口播，20 秒的片子放不下，
本机执行器跑到第 3 句才抛错、整条任务失败。根因同上次一样是**闸门缺失**：
`validate()` 只查了 `narration.length>2000`，没有时长检查；提示词只写「每秒3-4个汉字」，
**没告诉模型目标是多少秒**，模型根本不知道自己只有 20 秒预算。

**实测配音语速（Edge TTS，逐句合成 + 执行器 0.1 秒句间停顿，ffprobe 量）**：

| 样本 | 实测 |
|---|---|
| 11 字 / 1 句 | 3.24 s |
| 39 字 / 2 句 | 10.28 s |
| 156 字 / 6 句 | 39.52 s |
| 11 字 / 5 句 | 7.12 s |
| 67 字 / 4 句 | 18.44 s |
| 75 字 / 6 句 | 21.74 s |

**关键结论：字数不是唯一变量。** 同样 12 个字，合成 1 句 3.05 秒、3 句 4.61 秒、6 句 6.96 秒
——每段合成音频首尾有固定静音，**句子拆得越碎越浪费时间**。最小二乘拟合：

    seconds ≈ 字数 / 4.6 + 0.93 × 句数      （6 样本最大偏差 0.15 秒）

**反面教训（差点写错）**：最初只用单变量「3.9 字/秒」估，在短句多的文案上会**漏报**——
75 字 6 句实际要 21.7 秒，旧公式估成 19.7 秒会放过去，执行器必然失败。是采集 6 个样本重新
拟合才发现的。**只用一个数据点拟合常数很危险。**

落地：`edit-plan.js` 导出 `narrationChars/narrationSentences/narrationSeconds/narrationBudget`
（浏览器与 Node 同源）；`validate()` 加硬检查 `need > target - 0.2`（误差 ±0.15 秒，留 0.2 余量，
宁可偶尔多一次重排也不放过去）；`app.js` 的 `jyNarrationBudgetText(input)` 把上限写进提示词
（含「不要把一句话拆成几个短句」这条实测结论）；`jianying_edit.py` 报错改说「第 N/M 句就放不下」。

**顺手修掉一个 UX 陷阱**：`jobs/:id/retry` 只是把**旧方案**重新排队，剪辑失败（方案本身不合格）
时重跑多少次都一样。现在 `jianying-studio.js` 的失败卡片按钮改成「重新生成方案并重试」：
`restoreEditJob(job)` 还原表单+素材（`job.assets` 里有完整素材对象，缩略图不重取；**必须
`requestId=null`**，否则被服务端按 request_id 判成重复任务退回旧任务）→ `requestSubmit()` 走完整重提。
另外用户**自己填了口播文案**时模型改不动它，检测到这类错误直接抛给用户，不白烧三次模型调用。

测试：JS **39/39**（新增 5 条，含「6 样本估算误差 ≤0.2 秒」「句数同样影响时长」「75字6句必须拦」）、
Python **13/13**。真实 TTS 端到端复验：156 字 → 「第 3/6 句就放不下」；压缩到 67 字 → 实测 18.4 秒正常出片。
**6 个样本的闸门判定与执行器实际结果全部一致。**
