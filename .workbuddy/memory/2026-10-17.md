## 评估外部（ChatGPT）提议的「云端任务队列 + Cloud Bridge」方案

用户拿一份外部方案来问，方案主张：云端（WorkBuddy 网站）建队列/存储 + Mac 侧新增 Cloud Bridge 主动 HTTPS 领任务 → 注入本机 4191 → 剪映出草稿 → 云草稿同步。**结论：方向不错但现阶段不做；有两处事实性错误，且它买不到关键一环的确定性。**

### 核实到的事实（本次实测）

- **线上 `nail-content-workbench.app.workbuddy.host` 跑的是真 Node 后端**，不是静态站：`/api/health` → `{"ok":true,"service":"nail-content-workbench",...}`；`/api/trend/config` → 200；`/api/trend/collect` 超时(000)。部署记录 `~/.workbuddy/cloudstudio-deploy-history/a4663c044ef6b973_1792135829834.json`：`language:"node"`、`absolutePath=.../TFS_content_workbench/workbench`、`appId=wbapp_OVXOIXh914a31yrMdLVAOD`。
  → 所以「在云端加 `/api/editing` 路由」技术上可行；但**云端数据持久化**是真问题（该方案这条判断正确）。
- **仓库零对象存储、零云数据库**：搜 `腾讯云/SecretId/COS/bucket/genie/baas/supabase` 全部零命中。该方案推荐的腾讯云 COS + STS = 全新引入；本项目可改用 WorkBuddy 自带云服务（云数据库/文件存储/认证）。
- **单文件上传上限 100MB 属实**：`workbench/jianying-api.js:91` — `size > 100*1024*1024` → 413 `单个文件最大 100MB`。
- **该方案引用的是过时快照**：它看的 `127.0.0.1:4191` 写死 base 属 `main` 分支状态；分支 `feat/remote-access-tailscale` 已改为同源 `/api/jianying/` + 同源标记。
- **`/.cloud/` 方向**：`server.js:1353` 仅在 `JY_LOCAL` 时启用，反代上游固定为 `nail-content-workbench.app.workbuddy.host`（本机页面 → 云端接口）。

### 判断要点（记录给以后复用）

1. **分岔只在「请求怎么到达 Mac」**（隧道 vs 云队列），**汇合在「Mac 上的剪映出草稿」**；而**草稿上云 + 异地打开由剪映客户端决定 —— 换任何方案都绕不开，且尚未验证**。这是需求真正的成败点，不是 P1 小验证。
2. 该方案相对「Cloudflare 隧道」的净增量只有：Mac 离线可排队、大文件不经入站链路。而「免安装客户端」隧道同样给得到。**用隧道拿 90% 价值、5% 成本。**
3. 该方案说得对、值得吸收的点：①不要把 4191 暴露公网；②异步任务模型适合异地/移动；③`start-jianying.cjs` 每启随机 token 会卡住 Bridge（我们已用 `~/.wujiseason/remote-hosts` 落盘法解决一半，token 若要给 Bridge 需另写 0600 文件）；④重复下发的幂等（防同一请求建多份草稿）；⑤Mac 需保持图形用户会话登录。
4. 未验证前提（需实测）：**桌面版剪映的云草稿能否在手机剪映里打开**；素材是否随草稿一起上云。

## 澄清「能不能让 Cloudflare 隧道用 app.workbuddy.host」

- **不能。** 该域名由 `server: CloudStudio Gateway` 服务，DNS 在 WorkBuddy 手上；Cloudflare Tunnel 只能给「已加入自己 Cloudflare 账户的 zone」加路由。且它已绑定已发布应用（`appId=wbapp_OVXOIXh914a31yrMdLVAOD` / `sandboxId=60f3c6123d…`），改指向会弄坏线上页。
- **用户的误会**：以为「域名上的请求在本机制作」= 域名必须属于 Mac。实际只需要域名**指向** Mac，来源只有两个：`dreamyyxtmac-mini.tail7079d7.ts.net`（Tailscale 送）或 `no1dea.com`（NS 在 GoDaddy `ns59/ns60.domaincontrol.com`，要挪到 Cloudflare）。
- **远程设备打开线上页的实际行为（已核实代码）**：`jianying-studio.js:6-7` — 页面有 `meta[name="wj-local-service"]` 才走同源，否则退回 `http://127.0.0.1:4191`。线上页无此标记 → 手机上点「连接制作服务」连的是手机自己，必然失败。
- **一个容易忽略的好处**：打开 Mac 自己的地址，功能比线上页**更全** —— 本机 `server.js:1353` 的 `/.cloud/` 反向代理会把内容规划/趋势等云端接口转发到 `app.workbuddy.host`（`app.js:16`：本机页 endpoint = `origin + '/.cloud'`）。所以**一个地址就够**，不需要"门面 + 后台"两个。
- `jianying-api.js:11` 的 `WEB_ORIGIN` 白名单保留着，将来若要「线上页跨域直连 Mac」可直接用。

### ⚠️ `no1dea.com` 在用邮箱，不要整体挪 NS

实测：`A` 13.248.243.5 / 76.223.105.230（GoDaddy 停放页）；**`MX` → `no1dea-com.mail.protection.outlook.com`（Microsoft 365）**；`TXT` 含 `NETORGFT17614068.onmicrosoft.com` 与 `v=spf1 include:secureserver.net -all`。
→ 走 Cloudflare 隧道时，**优先「子域单独托管」**（在 GoDaddy 给 `nail` 加两条 NS 指向 Cloudflare 分配的 NS，Cloudflare 上把 `nail.no1dea.com` 建成独立 zone），主域与邮箱完全不动；或在 Cloudflare 直接新买一个域名（零迁移风险）。整体迁 NS 前必须核对 MX/SPF 是否导入完整。
