# 红狐风向采集

红狐与公开网页采集并行，任一采集失败不阻断另一个。两者均无可用作品时读取已有云端风向，不生成空依据的新计划。

## 五条取数线

| 线 | 内容 | 说明 |
|---|---|---|
| ① 抖音·最新 | 近 7 天爆款作品 | `sort_type='2'`（按发布时间） |
| ② 小红书·最新 | 近 7 天爆款笔记 | `sort_type='2'` |
| ③ 抖音·常青 | 综合排序样本，保留近一年 | 回答「什么题材长期跑得动」，**不按 7 天过滤** |
| ④ 小红书·全站最热 | 无关键词 + 日期区间 | 跨品类「当下在火什么」，补节日 / 时事维度 |
| ⑤ 小红书·关联词 | `relatedSearches` | 平台给的相关搜索词 + 笔记数 |

**必须传 `sort_type='2'`**：不传时抖音搜索按综合（相关性）返回，实测最新作品是几个月前的，
近 7 天过滤后一条都留不下（会误判成「平台没有相关内容」）。小红书同理。
③ 只取前 2 个关键词控制调用量，且**不并入 sources**（old 是它的目的，不是损失，故不计入 dropped）；
④ 同样不并入 sources —— 来源角标只留给「近 7 天·垂类相关」的作品，避免模型拿老内容或跨品类泛热冒充当下。

## 时令锚点

`trend-policy.js` 的 `seasons()/seasonWords()/searchKeywords()` 按当天日期推导节点：
窗口内节日 + 45 天内即将到来的节日（提前两三周铺内容）+ 所处季节。
节点同时注入红狐搜索词、搜索引擎词表和提示词【零】段。
**只收公历固定日期**：春节 / 七夕 / 中秋等农历节日每年公历日子不同，写死会算错，故不自动推导。
`searchKeywords()` 会把账号词限制在 max-3 以内，**保证至少 3 个位置留给时令词**。

店铺档案 → 账号矩阵 → 风向采集关键词：逗号分隔；留空按账号内容定位选择作品、经营或日常类关键词。
账号词最多 8 个 + 时令词最多 3 个（合计上限 11）。账号配置仍同步现有云端。

红狐 MCP 返回结果在服务端按发布日期限制近7天，再去重和计算标签参考分数。日期未知、过期及明显未来时间剔除并计数；支持Unix秒、毫秒和日期字符串。搜索只读取接口第一页（20 条），且 7 天窗口内可能确实很少，不能理解为平台没有相关内容。红狐返回的关联词笔记数量不是搜索量；累计点赞不是增长速度。

**已知不可用的红狐工具**（实测，勿再接入）：`douyin_get_daily_hot_rank` / `douyin_get_daily_surge_rank` /
`douyin_get_weekly_surge_rank` / `douyin_search_ai_articles`（返回空）；
`xiaohongshu_get_daily_hot_rank`（服务端 `structured_content must be a dict` 报错）；
`xiaohongshu_get_dark_horse_notes`（美甲类词一律返回 `3203 查询结果为空`）。
另：**同一 MCP 会话内多次调用会互相串扰**（返回空或旧结果），排查问题时每个用例要开新会话。

抖音 MCP 搜索工具失败时尝试 REST；小红书失败单独报告。页面通过 NDJSON 显示平台、关键词和当前操作，并在云端快照保存部分失败原因及剔除数量。

同一密钥、关键词和时间窗的成功完整结果缓存10分钟（缓存键含版本号 `v`，改采集逻辑时记得递增，否则旧缓存会串味）。重复并发请求合并；失败或部分失败结果不缓存。缓存仅在服务进程内存，重启清空，不共享到其他服务实例；密钥不存进缓存键（使用SHA256摘要）。

已有浏览器密钥继续有效。部署服务可设置 REDFOX_API_KEY 环境变量供连接同一服务的设备使用，前端只查询“是否配置”，不会拿到服务端密钥。浏览器已配置密钥优先于服务端密钥。没有把浏览器现有密钥自动迁移到服务器；不同机器运行各自本机服务也不会自动共享密钥。
⚠️ 一旦在部署环境设置该变量，任何拿到公开链接的人都能消耗该密钥的红狐积分（接口无鉴权）。

验证：自动测试覆盖时效、未知/未来日期、时间戳、账号关键词、时令节点与关键词名额保留、缓存隔离/合并、失败不缓存、MCP工具失败转REST和部分平台失败；浏览器模拟流式响应验证分段JSON和进度。不使用真实付费采集进行测试。
**一次完整采集约 22 次红狐调用**（9 关键词 × 2 平台 + 常青 2 + 关联词 1 + 全站热榜 1，不含 REST 兜底），按次扣积分。
